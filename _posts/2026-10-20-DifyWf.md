    【图谱 Schema 结构】

    - 关系：(P_Document)-[:BELONGS_TO_GROUP]->(P_IndustryGroup)
    - 关系：(P_Document)-[:BELONGS_TO_INDUSTRY]->(P_Industry)
    - 关系：(P_Document)-[:HAS_KEYWORD]->(P_Keyword)
    - 关系：(P_Document)-[:PUBLISHED_BY]->(P_Publisher) 仅在发布机构不为空时才存在

    【查询规则 - 必须严格遵守】
    1. 绝对不要直接用 `{p_title: 'xxx'}` 去精确匹配，因为用户的用词不可能和文档标题一字不差！
    2. 必须使用全文索引函数 `db.index.fulltext.queryNodes` 来进行模糊搜索。
    3. 用户的查询词请用 `OR` 连接，并用单引号包裹。例如：`'储能 OR 电池 OR 展望'`。
    4. 检索出文档后，请用 `OPTIONAL MATCH` 把它的行业和关键词带出来，方便大模型总结。
    5. 最终返回：d.p_title, d.p_summary, d.p_key_findings, d.p_pdf_path, d.p_year, d.p_region以及 score。
    6. 只输出纯 Cypher 语句，不要包含 ```cypher 标记，不要任何解释。
    7. 绝对不要输出 {{ 和 }} 符号，直接输出纯 Cypher 语句。
    8. 字符串匹配请直接用单引号，例如：'2026 冬季'

    【标准输出示例】
    CALL db.index.fulltext.queryNodes('doc_search', '‘天气’‘ OR ’‘气候’‘ OR ’‘预测’') YIELD node AS d, score WHERE score > 5 OPTIONAL MATCH (d)-[:BELONGS_TO_INDUSTRY]->(i:P_Industry) OPTIONAL MATCH (d)-[:HAS_KEYWORD]->(k:P_Keyword) RETURN d.p_title AS 标题, d.p_summary AS 摘要, d.p_key_findings AS 核心结论, d.p_pdf_path AS 本地路径, i.p_name AS 行业, collect(k.p_name) AS 关键词, d.p_year AS 年份, d.p_region AS 区域, score ORDER BY score DESC LIMIT 5

    【重要限制】
    9. 必须输出单行代码！绝对不能有换行符！不能有 \n！
    10. 如果用户问的是细节（比如“具体怎么说”、“详细内容”），搜索词请提取用户问题里的核心名词。

```python
from fastapi import FastAPI, HTTPException
import os

app = FastAPI()

@app.get("/read_md")
def read_md(filename: str):
    md_dir = r"E:\Archive\MD"
    
    # 拼接路径
    file_path = os.path.join(md_dir, filename)
    
    print(f"\n请求读 MD 文件: {file_path}")

    if not os.path.exists(file_path):
        raise HTTPException(status_code=404, detail="文件不存在")
        
    try:
        with open(file_path, 'r', encoding='utf-8', errors='ignore') as f:
            # 读取前 12000 字
            content = f.read(12000)
        return {"content": content}
    except Exception as e:
        raise HTTPException(status_code=500, detail=str(e))

if __name__ == "__main__":
    import uvicorn
    # 监听所有网络接口，端口设为 8000
    uvicorn.run(app, host="0.0.0.0", port=8000)

```

## 📝 总结（方案思路）
### 1. Neo4j全文索引 VS. MD向量库
- ✨ 一个是基于“词”的搜索，一个是基于“意”的搜索。如果提问的用词非常模糊，全文索引大概率返回 0 条结果，因为它不懂同义词，不懂口语化表达，更不懂错别字。但引入大模型的“Query 改写（查询重写）”能力，是可以把索引的范围尽量扩大。就是说在“输入问题”和“执行 Cypher”之间，多加一个 LLM 节点，让 AI 把口语化的问题翻译成标准术语。这样就能在有图谱的基础上，用Neo4j 全文索引就能把“模糊搜索”和“关系遍历”无缝地串联起来。只要不涉及到查极度细节的报告数据，这条链路都能实现查图谱真实准确的关联知识，并提炼洞察的功能。

- ✨ 把MD全量Embedding进入向量库，凭借语义相似度查到chunk文本，然后依此文本再搜图数据库。这样看似极度完美，其实是“向量粗排 + 图谱精排”的陷阱。根源在Embedding 进向量库和语义搜图数据库的维度无法完全拉齐。因为：① chunk没有带p_file,要强制把每个p_file都硬编码到chunk里面去才行得通。②报告文档的结构是大标题->中标题->小标题->论点->结论，不同的子标题极易被向量切块时写入同一个chunk，就算最后数据查到细节文字了，但是召回的碎片文字并没有那么干净完整，导致 LLM 再总结时极易前言不搭后语。

### 2. 解决方案：“先定靶子，再开枪”。
- 🔔 图谱优先检索（找源头）：

    利用图谱最大的优势——确定性与结构过滤，用户提问 -> LLM 提取意图 -> 在 Neo4j 里精准过滤出 P_Document（比如筛出“能源与环保”类的文档），并拿到文档的绝对路径 p_pdf_path。

- 🔔 局部向量检索（找细节）：

    拿到这几个文档的路径后，只把这几份文档的文本，通过Python代码读出来（或者临时查向量库，带上 p_file 的过滤条件），丢给 LLM 去提炼。
    
### 3. MD 原文细节字数突破（后续完善🎨）：
- 本地FastAPI微服务在读 MD 全文时，限制了截取前 12000 字。如果是换个 128K 上下文的长文本模型直接吞，在不考虑Token消耗的前提下无可厚非。Maybe有其他的性价比更好的方案，留待后续再继续完善😎）

### 4. 意图路由-问题分类器（后续实践🎨） 
- 多轮提问时需要用到Dify问题分类器，让LLM根据提问进行分支路由，避免问摘要也提取MD细节还浪费Token的尴尬。
- 在面临多报告比对等复杂问题时，可能还会创建or调用各种不同的SKill，另外再单篇去实践。

### 5. 教训经验（坑总是要踩一踩的😓）：
- 让Dify挂载本地文档，来获取 MD 文件原文的做法，以**失败告终**！
  
  原因： Dify 的底层代码是在 /tmp/code/ 下新建了一个临时目录来执行的，它默认的工作空间被锁死在了这里，禁止跨目录访问。或者说：Dify 官方在设计时，就不希望用户在代码节点里去读宿主机的本地文件。So，绕开 Docker 沙箱的限制，通过FastAPI提供微服务，然后在Dify里面插入一个新的 HTTP 请求节点来访问该FastAPI的读 MD 文件服务即可。

  😓按照下面的步骤操作后，powershell里面看上去是挂载成功的。但是，Dify里面执行Python代码时，依然报错No such file or directory :'/app/md_files' error.
    - ⛏Step1：首先打开Docker的配置文档（E:\dify-main\docker\docker-compose.yaml），找到sandbox 服务并添加上加载本地路径的映射（如下图）,保存。
    ![alt text](/assets/images/DifyWf/image-11.png)
    - ⛏Step2：使用管理员Powershell进入dify/docker，分别执行docker compose down和docker compose up -d，等Docker重启完成。
    - ⛏Step3：输入docker exec -it docker-sandbox-1 /bin/sh进入沙箱容器，执行 ls /app/md_files，看到输出显示 MD 文件，至此看上去挂载好了本地的 E:\Archive\MD 目录了。
    ![alt text](/assets/images/DifyWf/image-12.png)
